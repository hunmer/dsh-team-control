# 实现交接说明（给全新 Agent）

> 配套文档：[agent-team-plugin-prd.md](agent-team-plugin-prd.md) v1.0（已冻结）
> 你的任务：实现它。**不要重新讨论需求范围**，有冲突按 ADR 流程处理。

---

## 1. 你继承的上下文（30 秒版）

DSH 现有的 Agent Teams 有三个致命缺陷，本插件就是为解决它们而生：

1. **8 人硬上限且不可移除** → 要做成可配置 + 可回收
2. **只能同时 spawn，没有依赖编排** → 要做成 DAG 自动触发
3. **写域只是提示，能绕开** → 要做成执行层强制（四域）

其余需求（消息、状态查询、恢复、审计）都是从这三个问题的实测事故里长出来的。

## 3. 五条不可违背的约束

| # | 约束 | 违反后果 |
|---|---|---|
| **C1** | Worker 只挂 sidecar 提供的代理工具（fs/exec/net/env），禁用原生直连 IO | 权限可被绕过，整个 FR-3 失效 |
| **C2** | `event` 只增不改，`member_state` 必须能由 event 完全重建 | 崩溃恢复和审计都会不可信 |
| **C3** | 权限默认拒绝，deny 优先于 allow，多规则取最严 | 会出现「静默放行」的安全洞 |
| **C4** | 决策必须落盘为 `decision` 对象，消息只作通知 | 会重犯「成员空等 240s 超时」 |
| **C5** | 中断必须**同步**写状态，禁止残留 `running` | 会重犯「僵尸态误导 Lead」 |

## 4. 实现顺序（关键路径，别跳）

### M1 — 骨架跑通（先让它能转起来）

```
StateStore(SQLite) → event 流 + member_state 物化
Scheduler     → DAG 建图、依赖求值、ready 自动派发
WorkerRunner  → 拉起子进程、心跳租约、优雅中断
MessageBus    → 点对点 + 持久 + 回执
REST + SSE    → status / steps / events
```

**M1 完成判据**：AC-1、AC-2、AC-6、AC-7、AC-10 全过。

### M2 — 权限与容错（最难，也最值钱）

```
PermBroker    → 四域策略求值 + 唯一 IO 出口
               → scope_request / decision / scope_grant
Recovery      → resume / reconcile / lease 超时
```

**M2 完成判据**：AC-3、AC-4、AC-5、AC-8、AC-9、AC-11、AC-13 全过。

### M3 — 可用性

```
Web 面板（成员看板 / DAG / 时间线 / 权限矩阵 / 审批队列）
CLI（status / dag / logs / approve / report）
审计报告导出 + 成本统计
```

**M3 完成判据**：AC-12 过，面板能在真人操作下独立完成一次「看进度 → 审批 → 查报告」。

## 5. 自测要求（不许糊弄）

| 要求 | 说明 |
|---|---|
| 每条 AC 一个可复现脚本 | 放进 `tests/ac-*.ps1` 或 `.ts`，一条命令跑完 |
| 并发类必须重复跑 | AC-5（三人抢写）至少跑 **20 次**，丢更新次数必须为 **0** |
| 崩溃类必须真 kill | AC-9 用真实进程 kill，不允许 `mock crash` |
| 权限类必须验证「无副作用」 | AC-3 越界后要比对目标文件 hash，不是只看返回码 |
| 数据类必须对账 | `progress 事件数 == member_state.seq`，否则算失败 |

## 6. 我们踩过的坑（照抄必重犯）

| 坑 | 正确做法 |
|---|---|
| 用「阶段」记录进度，恢复时不知道做到哪 | 按**一次动作一条 event** 记 |
| 决策只发消息，成员在轮询中收不到，空等超时 | 决策写成文件/对象，消息只做提示 |
| interrupt 后只改内存状态 | 同步落库，100ms 内可见 |
| 依赖只用任务板标记 | 调度器主动求值并**唤醒**执行者 |
| 写域靠提示词约束 | 靠代理层强制拒绝 |
| 并发写靠「重试一次」 | 退避 + 可配置上限；≥3 写者考虑租约 |
| 成员摘要写「最终文件内容」 | 必须带 `as_of` 快照时间 |
| Lead 只看 `state` 判断死活 | 交叉校验 `list_agents`/租约，识别僵尸 |

## 8. 遇到歧义怎么办

1. 先查 PRD 术语表（第 4 章）与附录 B（新旧对照）。
2. **验收标准 > 功能描述**：两者冲突时以 AC 为准。
3. 需求之间冲突 → 取实现成本更低者，写一份 ADR 记录偏离，不静默改。
4. 不确定是否超范围 → 做最小可用版本，留扩展点，别自创需求。

## 9. 明确不要做的事

- ❌ 复用 DSH 内部 `spawn_teammate` / `team_task_*` 的实现（要独立）
- ❌ 做跨机分布式（单机先做透）
- ❌ 修改 DSH 内核源码
- ❌ 为了让 AC 通过而写死 mock（必须真实进程）
- ❌ 在 PRD 之外自创功能（先记 idea 到 backlog）

## 10. 第一天该做什么（建议）

1. 读 PRD 第 2.3 / 3 / 6 章，用 10 行话复述架构给自己听。
2. 建表（第 5 章 SQL 可直接用），写 `event.append()` 与 `state.rebuild()` 两个函数 + 单测。

> 先证明「事件流是唯一真相」这条能跑，后面所有功能都挂在这根主轴上。
