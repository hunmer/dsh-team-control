# ADR-005：调度竞态——建任务 settle 窗口 + 派发前重求值

- 状态：已接受
- 日期：2026-10-28
- 关联：FR-2.2 / FR-2.4 / AC-2

## 背景

Demo 实测发现真实缺陷：先 `POST /api/tasks` 建 B1、再 `POST /api/deps` 声明 A→B1 的常见建图顺序下，B1 在依赖声明前就被置 `ready` 并启动，导致 **B1 比 A 早 243ms 开始** —— 依赖形同虚设。

两个独立缺陷：
1. 建任务即求值启动，抢在依赖声明之前；
2. 任务一旦被置 `ready`，后续新加的依赖不会把它降级，派发循环也不复查依赖。

## 决策

1. **settle 窗口**：任务创建后 `settleMs`（默认 200ms）内不允许自动派发，留出「先建图、后声明依赖」的窗口；期间 tick 会继续求值但不会启动。
2. **派发前重求值**：派发循环对每个候选重新跑 `readiness()`；不满足则降级为 `pending`（若依赖永不可满足则 `blocked`）。
3. **内联依赖**：`POST /api/tasks` 支持 `deps:[{from,condition,artifactPath}]`，与任务创建同事务插入，彻底消除该竞态（推荐用法）。
4. **兜底 tick**：每 150ms 对所有团队求值一次，保证「没有任何显式事件」时队列仍能推进（例如 queued 成员晋升、重试到点）。

## 后果

- ✅ Demo 中 `A.done → B1.start` 从 **-243ms** 修正为 **+1ms**，且仍然事件驱动（不是等 tick）。
- ✅ 建图顺序不再敏感：先建任务后加依赖、或直接用 `deps` 内联，行为一致。
- ⚠️ 极短任务可能因 settle 窗口延后最多 200ms 启动；对 Agent 编排可忽略，且可用 `DSH_TEAM_SETTLE_MS` 调整（当前常量在 `Scheduler` 构造参数）。
- ⚠️ 依赖在任务已 **running** 后追加，仍无法回滚已开始的执行；`POST /api/deps` 不做运行期阻断（这是建图顺序问题，不是调度问题），文档已标注推荐内联声明。
